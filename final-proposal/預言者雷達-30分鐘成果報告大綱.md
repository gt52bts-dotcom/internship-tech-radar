## 一句話核心主張

我做的不是單純蒐集 AWS 新聞，而是一套可以把雲端新功能從「看到消息」推進到「可評估、可報價、可驗證、可交接」的 AI PM 技術雷達流程。它的價值在於降低新技術判斷的資訊落差，讓人可以更早知道一項技術值不值得投入 PoC。

## 30 秒版電梯簡報

雲端服務更新很快，但企業真正困難的不是「知道有新功能」，而是判斷它和公司有沒有關係、要花多少錢、風險能不能停、PoC 成功後能證明什麼。我的專案把這件事拆成五個 Skill：掃描、比較、評估、驗證、報告。AI 協助整理公開證據、人類負責決策，最後產出可讀的評估報告、成本預估、PoC 證據和清理紀錄。這套流程目前已用 Lambda、S3 Files、WorkSpaces AI Agents 等案例測出不同類型的技術價值與流程盲點。

## 投影片逐頁大綱

### 1. 封面：預言者雷達

主標題：《預言者雷達：看見技術的下一步》
副標題：用 AI PM 把雲端新功能轉成可決策的 PoC 證據鏈
要講的話：這份報告不是在介紹單一 AWS 服務，而是在說明我如何建立一套判斷新雲端技術是否值得投入的流程。

### 2. 先講結論

畫面重點：

- 我完成一套 S1-S5 技術雷達流程。
- 每篇技術新聞都會被轉成可比較、可報價、可驗證的候選。
- PoC 不再是「想做就做」，而是必須先回答：值不值得做、要證明什麼、風險能不能停。

要講的話：如果只看新聞，很容易覺得每個新功能都很有趣；但企業需要的是可判斷的證據，不是新奇感。

### 3. 問題：新技術太多，但決策資訊太晚出現

畫面重點：

- AWS、GitHub、雲端服務更新頻繁。
- 新功能公告通常只說「它能做什麼」，不會直接告訴企業「是否值得試」。
- 成本、限制、區域支援、清理風險，常常到 PoC 之後才被發現。

要講的話：我的專案要解決的是資訊時序問題，讓成本與風險在 Skill 3 就先出現，而不是到 Skill 4 才踩雷。

### 4. 公司情境：為什麼這件事對雲端團隊有用

畫面重點：

- 雲端團隊需要持續追蹤新服務與架構趨勢。
- 不是每個新功能都適合直接部署。
- 實習專案需要兼顧學習、可展示、低風險、可驗證。

要講的話：這個專案對公司最大的效益，是建立一個「先判斷再投入」的流程，而不是讓人靠直覺挑技術。

### 5. 原本的痛點

畫面可用「以前」與「現在」對照：

- 以前：看到文章後先做 PoC，成本與限制晚點才整理。
- 現在：Skill 3 先產出解釋、評分、報價、架構圖，再由人決定要不要進 Skill 4。
- 以前：PoC 成功容易只記錄結果。
- 現在：PoC 必須保留部署證據、資源盤點、清理證據。

要講的話：我後來修正最多的地方，就是把人類決策點往前移，把證據保留往後延伸。

### 6. 解法總覽：五個 Skill

畫面用一張流程圖：

1. Skill 1：掃描雲端新功能與文章。
2. Skill 2：把候選整理成可比較的提案。
3. Skill 3：解釋文章、評分、報價、產生架構圖，讓人決定是否 PoC。
4. Skill 4：在明確核准後做低風險 PoC，收集 runtime 證據。
5. Skill 5：整理最終報告、證據、限制與下一步。

要講的話：這五段不是流水線而已，重點是每一段都有不同責任。AI 可以整理與執行，但是否值得花錢部署，仍由人決定。

### 7. AI PM 的角色

畫面重點：

- AI 負責：蒐集、整理、測試、產出報告、追蹤待辦。
- 人類負責：選題、核准成本、確認風險、判斷價值。
- GitHub 是共同記憶，避免不同 AI 或不同電腦接不上。

要講的話：我不是把 AI 當聊天工具，而是把它當成專案協作者。它會幫我補文件、跑測試、記錄決策，但我需要一直校正它的判斷標準。

### 8. 方法一：文章先被翻成人看得懂的問題

畫面重點：

- Skill 1 不只抓標題，也產生文章解釋層。
- 報告要先回答：這篇文章在講什麼、以前怎麼做、現在改變什麼。
- 不能只節錄原文，要舉出實體應用情境。

要講的話：這是我後來特別要求修正的地方。主管或決策者不會只想看原文摘要，而是要知道這個技術到底能解決什麼現實問題。

### 9. 方法二：Skill 3 是真正的決策關卡

畫面重點：

- Skill 3 必須先產出報價單。
- Skill 3 必須列出評分細項。
- Skill 3 必須產生架構圖，讓人知道 PoC 會建什麼。
- Skill 3 不能自己決定跳過或進入 PoC。

要講的話：這段是整套流程最關鍵的設計。PoC 前，人要能同時看到技術價值、成本、風險、驗證範圍。

### 10. 方法三：評分不再被文件完整度灌高

畫面重點：

- 早期問題：AWS 文件越完整，候選越容易拿高分。
- 修正後：評分只看技術性質與 PoC 可驗證性。
- 文件完整度只作為 review note 或 blocker，不直接加分。

要講的話：WorkSpaces AI Agents 是這個修正的關鍵案例。它技術上很有趣，但目前 PoC 能證明的事情有限，所以不應該拿到過高分數。

### 11. 五個評分構面

畫面放表格：

| 構面 | 問什麼 | 權重 |
| --- | --- | ---: |
| 技術價值 | 相對現有做法有多大改善 | 30% |
| 可驗證性 | PoC 能否證明核心主張 | 20% |
| 導入前置條件 | 需要多少額外條件或審核 | 20% |
| 可控制性 | 執行中能不能停止風險 | 15% |
| 可逆性與清理 | 清理後能不能停止成本與影響 | 15% |

要講的話：這張表要讓主管知道分數不是憑感覺，而是有固定結構。每個候選都要列出細項分數。

### 12. 方法四：成本估算提前到 PoC 前

畫面重點：

- Skill 3 產生低、預期、高三種情境。
- 報價是公開 rate card 預估，不是假裝是正式採購報價。
- 需要標明最貴項目與成本是否能靠 cleanup 停止。

要講的話：我學到最重要的一點是，低成本不是只看總額，而是看成本型態。有些資源清掉就停止，有些月費一旦觸發就退不掉。

### 13. 方法五：Skill 4 不再只看截圖

畫面重點：

- 原本想用 Infrastructure Composer 截圖讓人確認。
- 後來改成結構化資源盤點。
- 程式能比對 CloudFormation 實際資源與報價資源。
- 截圖可以輔助人看，但不能當主要證據。

要講的話：這是流程成熟的一個轉折。截圖看起來直覺，但程式無法可靠判讀 PNG；資源盤點才是可自動驗證的證據。

### 14. 系統成果總覽

畫面重點：

- 可重跑的 S1-S5 CLI 核心。
- 五個 Skill package。
- Skill 3 HTML 決策報告。
- PoC 架構圖與報價單。
- Skill 4 recipe registry。
- Skill 5 最終報告與 cleanup 證據。
- GitHub 交接與日誌機制。

要講的話：這些成果不是一次性文件，而是可重複使用的流程包。

### 15. 成果展示：Skill 3 決策報告

畫面放 Skill 3 HTML 報告截圖或片段：

- 文章在講什麼。
- PoC 最小架構圖。
- 評分細項。
- 成本預估。
- 是否能進 Skill 4。

要講的話：這張報告是人類決策前最重要的產物。它讓主管不用先看一堆 JSON 或 AWS 文件，就能知道要不要繼續。

### 16. 成果展示：Skill 4 驗證與清理

畫面放資源盤點或 cleanup 摘要：

- 建立哪些資源。
- 實際資源是否和報價一致。
- 執行了哪些權限動作。
- cleanup 是否確認完成。

要講的話：PoC 的價值不是只看「有沒有成功部署」，還要看能不能留下可信證據、能不能清掉、能不能交給別人複查。

### 17. 案例一：Lambda 自主管理程式碼儲存

畫面重點：

- 主張：Lambda 可直接引用 S3 中的程式碼版本。
- PoC 價值：證明 reference 模式可建立、可 invoke、可 cleanup。
- 學到：低成本、請求型資源，cleanup 可以有效止血。

要講的話：這是比較適合 PoC 的案例，因為驗證目標明確、成本低、風險可控。

### 18. 案例二：S3 Files

畫面重點：

- 主張：S3 bucket 可以像檔案系統一樣被掛載。
- PoC 價值：驗證 VPC、EC2、mount target、filesystem、S3 bucket 之間能否串起來。
- 學到：Skill 3 的架構圖和報價單已經能讓人看出價值，Skill 4 則補上實際可部署性與清理證據。

要講的話：這個案例說明 PoC 的價值不是取代 Skill 3，而是把「看起來合理」變成「真的能在帳號裡建立並清掉」。

### 19. 案例三：WorkSpaces AI Agents

畫面重點：

- 主張：AI agent 可以操作桌面應用。
- 初期吸引點：可能解決 AI 幫忙登入 AWS Console 看 Infrastructure Composer canvas 的需求。
- 修正後判斷：目前更好的做法是結構化資源盤點，不需要 AI 看 PNG。
- 結論：技術有趣，但以目前範圍不值得進 live PoC。

要講的話：這是流程正常運作的證明。高熱度技術不代表就該做 PoC；如果 Skill 3 已經回答關鍵問題，就應該停止。

### 20. WorkSpaces 案例暴露的成本盲點

畫面重點：

- 月費一旦觸發，cleanup 不能退款。
- 低用量情境不能假設 0 個使用者卻有串流時數。
- 成本型態必須納入決策。

要講的話：這個案例逼出框架盲點：以前我只問「總額多少」，後來發現更該問「這筆錢能不能靠停止資源控制」。

### 21. 專案對我的效益

畫面重點：

- 把模糊題目拆成可執行流程。
- 學會用證據而不是直覺評估技術。
- 學會管理 AI 產物品質，不盲信 AI。
- 從寫程式進一步到設計決策流程。

要講的話：這個專案讓我從「把功能做出來」轉向「讓決策更可靠」。這比單純完成一個 demo 更有價值。

### 22. 專案對公司的效益

畫面重點：

- 保留可交接的證據鏈。

要講的話：即使這套流程還不是正式產品，它已經能作為技術評估與實習研究的工作方法。

### 23. 嚴格講限制

畫面重點：

- 目前不是完整上線系統。
- 成本估算不是即時 AWS Pricing API 或正式採購報價。
- S4 recipe 仍需逐項補充，不可能所有 AWS 新功能自動部署。
- 部分報告仍需要持續改善語言與視覺品質。
- 公司環境、權限、合規仍需人工確認。

要講的話：我不會把它包裝成萬能系統。它目前最強的是「把技術新聞變成可討論、可驗證的決策材料」。

### 24. 新穎性與進步性

畫面重點：

- 新穎性：把 AI PM、雲端技術雷達、PoC 報價、清理證據串成一條流程。
- 進步性：不是只做新聞摘要，也不是只做一次 PoC，而是讓每一步都有決策責任。
- 與一般做法差異：一般做法偏人工追新聞或事後寫報告；本專案把決策前移、證據後留。

要講的話：這段要回應 mentor 提醒的論文式問題：以前少有人這樣做，跟相近做法相比進步在哪裡。

## 主管可能會問的問題

1. 這套流程和一般技術研究報告差在哪裡？
   回答方向：一般報告偏整理資訊；這套流程會把資訊轉成決策關卡、成本、驗證條件與清理證據。

2. AI 在這裡到底做了什麼？
   回答方向：AI 做的是專案協作、文件整理、測試、報告產生與流程追蹤；但成本核准、PoC 進入與最終判斷仍由人負責。

3. 為什麼不每篇都直接 PoC？
   回答方向：PoC 要回答文件不能回答的問題。若 Skill 3 已經能判斷不值得，停止就是正確結果。

4. 成本估算準不準？
   回答方向：目前是公開價格表的預部署估算，不是正式採購報價；價值在於提前暴露成本形態與高風險項目。

5. 這套能不能產品化？
   回答方向：目前是可重做的流程包，不是完整產品。若要產品化，還需要正式權限、登入、監控、CI/CD、審計與更完整 GUI。
