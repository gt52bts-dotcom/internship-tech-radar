# 停止案例：不是做不出來，是不該硬做

## 核心訊息

這兩個案例的價值不是「失敗」，而是流程學會在 Skill 3 擋下不值得進 Skill 4 的 PoC。企業情境裡，能有證據地停止，比硬做一個看起來能跑的 demo 更重要。

## 什麼叫硬做

在 Skill 3 已經看出缺少部署前提、成本不可逆、缺少實作細節、缺少可部署 recipe，或 PoC 成功後也不會新增決策證據時，仍為了展示而臨時縮小範圍、編一個簡化架構、建立 AWS 資源，並把它包裝成 PoC 成功。

## 兩個停止案例

| 案例 | 容易硬做的方式 | Skill 3 擋下的理由 | 對專案的價值 |
|---|---|---|---|
| WorkSpaces AI Agents | 把「AI agent 操作桌面」硬縮成建立 WorkSpaces / AppStream 入口。 | 真正桌面 agent session 可能觸發 Windows 使用者月費，cleanup 不能退費，也牽涉代理觀看或操作桌面的合規邊界。 | 讓流程學會：能建入口不等於值得 PoC；要先補 recipe、成本、合規與第二段核准。 |
| Amazon Quick Suite | 因為是 AWS 官方新聞，就用廣告詞推一個簡化 agent demo。 | 文章多是產品願景與效益宣稱，缺少足夠實作步驟、資源組合、API 與可驗證最小架構。 | 讓流程學會：官方來源不等於可部署證據；沒有做法就不能硬編 PoC。 |

## 講稿

> 這兩個案例我不會說成單純失敗，而是停止案例。它們原本都很容易被 AI 硬做成一個簡略版 demo：WorkSpaces 可以只建入口，Quick Suite 可以只照廣告詞想像架構。但這樣做出來的東西不會增加決策證據，反而會帶來成本、合規或誤導風險。所以我把「不要硬做」寫成 Skill 3 的規則：PoC 要先回答它要證明什麼，成功後決策者會多知道什麼；回答不出來，就停在 Skill 3。
