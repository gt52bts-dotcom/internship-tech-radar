# Skill 3 評分準則與四個案例對照

這份是給人看的版本，用來回答一件事：為什麼有些新聞可以進 PoC，有些新聞分數看起來不低卻仍然要停止。

## 一句話結論

Skill 3 不是在問「這篇新聞看起來酷不酷」，而是在問：

> 這個技術有沒有明確價值、能不能被小型 PoC 驗證、我們帳號與地區能不能做、風險能不能停住、資源能不能收乾淨。

所以最後不是只看分數。要進 Skill 4，必須同時滿足：

- 加權分數達到 `3.75 / 5` 以上。
- 沒有 PoC blocker。
- 成本估算已完成，而且有可接受的核准上限。
- 有已登錄、可部署、可清除的 Skill 4 recipe。
- 有具名人類核准。

## 目前正式評分維度

| 維度 | 權重 | 這一項在問什麼 | 高分代表 | 低分代表 |
| --- | ---: | --- | --- | --- |
| 技術價值 | 30% | 這個功能到底改善了什麼？ | 有明確 before / after，且能說出對工作流程或架構的實質改變。 | 只有產品宣傳、名詞堆疊，看不出真的解決什麼問題。 |
| 可驗證性 | 20% | 能不能用小型 PoC 驗證核心主張？ | 有明確成功條件，例如部署成功、讀寫成功、invoke 成功、設定可回查。 | 只能說「看起來有用」，但沒有可測量、可重現的驗證方式。 |
| 導入前提 | 20% | 要開始做之前，需要多少外部條件？ | 標準 AWS 服務、目標 Region 可用、權限與環境要求清楚。 | 需要既有企業環境、特殊帳號權限、授權模式或 Region 支援仍不明。 |
| 風險與停損條件 | 15% | 出問題時能不能停？ | 有明確 stop condition、成本上限、逾時中止、不得繼續條件。 | 可能進入不可控支出、長時間資源、或操作範圍不清楚。 |
| 可逆性與清除 | 15% | 做完能不能收乾淨？ | recipe 有 cleanup strategy，也能回查資源確實消失。 | 有月費、使用者授權、外部狀態或無法回復的成本。 |

加權公式：

```text
總分 =
技術價值分 * 0.30 +
可驗證性分 * 0.20 +
導入前提分 * 0.20 +
風險與停損分 * 0.15 +
可逆性與清除分 * 0.15
```

每個維度都是 `0` 到 `5` 分。

## 分數怎麼看

| 分數區間 | 人類解讀 |
| --- | --- |
| `4.25 - 5.00` | 很適合做受控 PoC。通常技術價值清楚、驗證路徑明確、成本與清除都可控。 |
| `3.75 - 4.24` | 勉強達到 PoC 門檻，但要仔細看 blocker、recipe、成本與 Region。 |
| `3.00 - 3.74` | 有研究價值，但不應直接建立 AWS 資源。通常是證據、recipe 或停損條件不夠。 |
| `0 - 2.99` | 不適合進 PoC。可能技術主張太抽象、前置條件太多、成本或清除風險太高。 |

## 四個案例對照

| 案例 | 結果 | Skill 3 分數 | 為什麼 |
| --- | --- | ---: | --- |
| Lambda 自主管理程式碼儲存 | 成功案例 | `4.15 / 5` | 官方文章直接說明做法；PoC 可以驗證 Lambda 是否能參照自管 S3 code package 並成功 invoke；成本極低；資源可清除。 |
| S3 Files | 成功案例 | `4.4 / 5` | 技術主張具體：讓 S3 bucket 以 file system 方式被掛載；PoC 可驗證 EC2 mount、S3 讀寫雙向同步；成本與 cleanup 都可控。 |
| WorkSpaces AI Agents | 停止案例 | `2.65 / 5` | 技術價值高，但涉及桌面代理操作、串流環境、授權與可能月費；第一階段 recipe 只能驗證基礎設施入口，不能證明 AI 真的完成桌面任務；可逆性低。 |
| Amazon Quick Suite | 停止案例 | `3.7 / 5` | 官方新聞有產品價值主張，但實作細節不足；沒有可部署 recipe；缺少能包成 Skill 4 PoC 的最小架構與成功條件，所以分數接近門檻仍不能做。 |

## 兩個成功案例為什麼能過

### Lambda

Lambda 的亮點不是「用了 S3」而已，而是：

- 官方已經明確說明 Lambda 可以使用自主管理的 S3 程式碼儲存。
- PoC 的成功條件很小但很有意義：CloudFormation 建立 Lambda，Lambda 使用 `REFERENCE` 模式，最後 invoke 成功。
- 成本估算非常低，主要是小型 S3 / Lambda 請求與短時間測試。
- cleanup 可以直接刪除 stack、bucket 與測試物件。

因此它適合當成功案例：它把「新聞功能」變成「本帳號、本地區、本權限路徑可跑通」的證據。

### S3 Files

S3 Files 的亮點是它把 S3 bucket 從 object storage 的使用方式，延伸成可被 EC2 當作 file system 操作。

它能過的原因：

- 技術改變明確：S3 object 可以透過檔案系統介面讀寫。
- PoC 成功條件直接對應新聞主張：EC2 mount target、從 S3 讀、從掛載點寫回 S3。
- 可以用小型測試控制成本。
- cleanup 可以回查 CloudFormation stack、bucket、mount 相關資源是否清除。

因此它不是只「看起來有趣」，而是有清楚的 AWS 資源關係可以被驗證。

## 兩個停止案例為什麼停

### WorkSpaces AI Agents

WorkSpaces 的技術價值很高，但它被停止不是因為沒價值，而是因為 PoC 風險和可逆性不夠好。

主要問題：

- 可能牽涉 Windows streaming user、AppStream / WorkSpaces Applications、agent session、授權與月費。
- 第一階段最多只能驗證 fleet、stack、AgentAccessConfig、短效 streaming URL。
- 它不能證明 AI agent 真的在桌面完成企業任務。
- 一旦開啟完整 session，可能產生月費或不可退款成本。

所以這個案例適合當「高價值但不能貿然 PoC」的停止案例。

### Amazon Quick Suite

Quick Suite 的問題是相反：它的宣傳價值很明顯，但工程細節不夠。

主要問題：

- 文章偏產品宣傳，缺少可以直接部署的最小架構。
- 沒有對應的 Skill 4 recipe。
- 沒有明確資源清單、成功條件、IAM 邊界、cleanup 範圍。
- 即使分數有 `3.7 / 5`，仍低於 `3.75 / 5`，而且有 blocker。

所以它適合當「官方新聞也可能被擋下」的案例：不是 AWS 官方就一定能 PoC。

## 最重要的展示角度

這套評分準則真正要展示的是：

- AI 不是只幫忙找新聞，而是把新聞拆成能不能驗證的工程問題。
- 成功案例證明：本帳號、本地區、本權限路徑真的可以跑。
- 失敗案例證明：系統不是看到 AWS 官方文章就盲目部署。
- 分數只是第一層，真正的 gate 是「分數 + blocker + 成本 + recipe + 人類核准」一起判斷。

## 注意版本差異

Lambda 與 S3 Files 是較早完成的成功案例，當時 artifact 使用四維度評分：

```text
技術價值 35%
導入前提 25%
可驗證性 25%
風險與停損 15%
```

後來依照評分校正，正式模型改成五維度，新增「可逆性與清除」並調整權重。這不影響兩個成功案例作為 PoC 成功證據，但在簡報時建議用目前五維度準則講方法，案例表則標示它們是當時 artifact 的實際分數。
