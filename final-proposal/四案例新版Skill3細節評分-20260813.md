# 四案例新版 Skill 3 細節評分

本文件依 2026-08-13 版 `Skill 3 評分準則` 重新評估四個展示案例。評分來源是重新以目前 `agentic_cloud_radar/rubric.py` 跑出的 Skill 3 artifacts，權重如下：

| 構面 | 權重 | 加權方式 |
|---|---:|---|
| 技術能力 | 0.30 | 分數 × 0.30 |
| 證據可驗證性 | 0.20 | 分數 × 0.20 |
| 導入前置條件 | 0.20 | 分數 × 0.20 |
| 可控制性與停止機制 | 0.15 | 分數 × 0.15 |
| 可逆性與終止 | 0.15 | 分數 × 0.15 |

通過規則：加權總分 `>= 3.75 / 5`，且沒有否決門檻、沒有 blocker，才算可進入 Skill 4。達分不等於自動部署，仍需人工核准成本與 PoC。

## Lambda 自主管理程式碼儲存

結論：成功案例。它的重點不是「新聞很新」，而是公開文章已給出可操作機制：Lambda 可以用 S3 bucket 中的 code package reference，不再由 Lambda 複製到 Lambda-managed storage；Skill 4 recipe 也能把這件事變成建立、呼叫、清除的受控驗證。

| 構面 | 分數 | 權重 | 加權分 | 評分理由 |
|---|---:|---:|---:|---|
| 技術能力 | 4 | 0.30 | 1.20 | 原文明述質性改善並說明改變機制：用自主管理 S3 儲存貯體參照程式碼，降低傳統複製與儲存限制問題；但未提供足夠量化改善數據，所以不是 5。 |
| 證據可驗證性 | 5 | 0.20 | 1.00 | 已有可部署 recipe，可用 `S3ObjectStorageMode=REFERENCE`、S3 object version、Lambda invoke 結果驗證核心主張。 |
| 導入前置條件 | 4 | 0.20 | 0.80 | 需要建立 Lambda、S3、IAM、CloudFormation / CloudWatch 等標準資源，但不需要新的授權或跨部門審核。 |
| 可控制性與停止機制 | 4 | 0.15 | 0.60 | 停止條件已定義，若部署或 invoke 不符合預期，流程能停在人工判斷，不硬推到下一步。 |
| 可逆性與終止 | 5 | 0.15 | 0.75 | 資源可透過 stack cleanup 移除，費用屬低量按用量計費，recipe 有清除與回查方式。 |

總分計算：`1.20 + 1.00 + 0.80 + 0.60 + 0.75 = 4.35 / 5`。

補充：預期 PoC 估算約 `USD 0.000749`，高情境約 `USD 0.003387`，建議核准上限 `USD 0.05`。新版判斷是可進 Skill 4，但仍需人工核准。

## S3 Files

結論：成功案例。它適合進 PoC，因為核心主張很明確：S3 bucket 能以 file system 方式被存取；Skill 4 能透過 EC2 mount、S3-to-mount 與 mount-to-S3 雙向檔案驗證，補足只讀新聞無法證明的部署與 runtime 證據。

| 構面 | 分數 | 權重 | 加權分 | 評分理由 |
|---|---:|---:|---:|---|
| 技術能力 | 4 | 0.30 | 1.20 | 原文明述質性改善並說明改變機制：讓 S3 bucket 可作為 file system 存取；但公開文章沒有足夠量化效能或成本改善，所以不是 5。 |
| 證據可驗證性 | 5 | 0.20 | 1.00 | 已有可部署 recipe，可用 EC2 掛載、讀寫檔案、S3 object 回查驗證核心主張。 |
| 導入前置條件 | 3 | 0.20 | 0.60 | 需要 VPC、EC2、SSM、S3 bucket、mount target / file system 相關能力，前置資源比 Lambda 重。 |
| 可控制性與停止機制 | 4 | 0.15 | 0.60 | 停止條件已定義，若掛載、同步或回查失敗，可停在人工判斷與資源盤點，不繼續包裝成成功。 |
| 可逆性與終止 | 5 | 0.15 | 0.75 | recipe 有清除策略與回查；測試資源可刪除，按用量與短時間資源為主。 |

總分計算：`1.20 + 1.00 + 0.60 + 0.60 + 0.75 = 4.15 / 5`。

補充：預期 PoC 估算約 `USD 0.04719`，高情境約 `USD 0.150963`，建議核准上限 `USD 0.20`。新版判斷是可進 Skill 4，但仍需人工核准。2026-08-13 這輪 S3 Files PoC 目前仍停在 cleanup 前人工確認狀態，不能在未核准時清除。

## WorkSpaces AI Agents

結論：停止案例。它不是沒有技術價值，而是目前能低成本驗證的部分只到 WorkSpaces / AppStream agent access 基礎設施入口，不能證明完整 AI agent 操作桌面工作流程；而且完整 session 牽涉授權、合規與可能不隨 cleanup 退回的月費型成本。

| 構面 | 分數 | 權重 | 加權分 | 評分理由 |
|---|---:|---:|---:|---|
| 技術能力 | 4 | 0.30 | 1.20 | 原文明述質性改善並說明機制：AI agent 可操作桌面應用，技術方向有價值；但缺乏可量化改善數據。 |
| 證據可驗證性 | 3 | 0.20 | 0.60 | recipe 可驗證基礎設施入口、fleet / stack / streaming URL，但不能驗證真正的 AI 桌面任務完成，因此只能證明部分主張。 |
| 導入前置條件 | 1 | 0.20 | 0.20 | 目標區域需確認、服務組合多、授權與合規前提重，已超出單一低摩擦 PoC。 |
| 可控制性與停止機制 | 3 | 0.15 | 0.45 | 有停止條件，但未知項目多，AI 可能太晚承認證據不足；尤其是基礎設施成功不等於完整桌面 agent 任務成功。 |
| 可逆性與終止 | 1 | 0.15 | 0.15 | 完整 Windows streaming user session 可能觸發月費或已消耗 session 成本，cleanup 不能保證止血。 |

總分計算：`1.20 + 0.60 + 0.20 + 0.45 + 0.15 = 2.60 / 5`。

停止理由：未達 `3.75 / 5`，且 `可逆性與終止 = 1` 觸發否決。主要 blocker 是 `compliance_review_required` 與 `veto_reversibility_and_cleanup`。這個案例應先補授權、合規、成本與第二階段 proof question，不應直接進 live Skill 4。

## Amazon Quick Suite

結論：停止案例。它的問題不是「官方新聞不可信」，而是官方新聞仍然可能只有產品願景、使用情境和效益描述；如果沒有資源清單、資料流、API、權限、部署步驟或 cleanup 範圍，AI 不能自己編出一個 PoC 當成可驗證證據。

| 構面 | 分數 | 權重 | 加權分 | 評分理由 |
|---|---:|---:|---:|---|
| 技術能力 | 4 | 0.30 | 1.20 | 文章明確描述 agentic teammate、回答問題、整理企業資料、觸發行動等質性改善，有技術價值；但不是可量化效益。 |
| 證據可驗證性 | 1 | 0.20 | 0.20 | 來源缺少可部署實作細節；沒有足夠 resource list、資料流、權限、成功條件或 recipe，AI 想像的測試不能提高可驗證性。 |
| 導入前置條件 | 4 | 0.20 | 0.80 | 目前主要前提是目標區域與服務可用性待確認；尚未暴露出明確月費或組織級採購條件，但也因缺 recipe 不能說已可導入。 |
| 可控制性與停止機制 | 3 | 0.15 | 0.45 | 有停止條件與 blocker，但未知項目偏多；若 AI 沒承認資訊不足，很容易把行銷敘述硬做成 demo。 |
| 可逆性與終止 | 3 | 0.15 | 0.45 | 沒有已登錄 recipe，所以 cleanup 範圍不明；目前不是確定不可逆，而是無法確認清除是否真的止血。 |

總分計算：`1.20 + 0.20 + 0.80 + 0.45 + 0.45 = 3.10 / 5`。

停止理由：未達 `3.75 / 5`，且 `證據可驗證性 = 1` 觸發否決。主要 blocker 是 `implementation_detail_insufficient`、`veto_verifiability`、`no_deployable_recipe`。正確下一步是找更具體的官方文件、workshop、API 文件或 sample repo，再回填 S1/S2/S3，不是直接部署。
