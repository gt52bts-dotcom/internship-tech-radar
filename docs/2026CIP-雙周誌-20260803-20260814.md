# 2026CIP 雙周誌（2026-08-03 至 2026-08-14）

## 本期工作主軸

本期我把「預言者雷達」從可以執行的 AWS PoC 流程，收斂成一套可向主管說明的技術決策方法。核心不是單純展示 AI 會搜尋新技術或部署雲端資源，而是建立一條從來源掃描、候選比較、部署前評估、受控 PoC 驗證到證據報告的完整鏈條，讓每個候選在投入成本前先看見價值、風險、成本、可驗證性與停止條件。

2026-08-14 已完成預言者雷達成果發表。現場回饋整體正向，大家認為成果表現不錯；這項回饋目前以使用者回報作為紀錄，後續若有正式評語再補入日誌或成果文件。

## 主要成果與影響

### 1. 完成預言者雷達成果發表

本期最重要的成果是完成 8/14 對部門的專案成果發表。簡報主軸聚焦在「預言者雷達如何幫助人提前判斷一項新雲端技術值不值得做 PoC」，並用成功與停止案例證明流程不只會推薦，也能在證據不足、成本不可逆或合規風險過高時停止。

這次發表讓專案從內部工程成果轉成可被主管理解的決策工具：主管不需要看完整程式碼，也能透過 Skill 1 到 Skill 5 的輸出理解來源證據、評分依據、成本估算、PoC 範圍、runtime 驗證與限制。

### 2. 將五個 Skill 收斂成可交接的決策流程

本期把 Skill 1 到 Skill 5 的定位重新整理清楚：

| Skill | 本期收斂後的定位 |
|---|---|
| Skill 1 Scan | 把官方來源拆成可採信證據與待驗證推論，不把 AI 推測當成事實。 |
| Skill 2 Compare | 整理候選卡與比較依據，讓人類選定唯一候選，不讓系統自動替人做最終選擇。 |
| Skill 3 Evaluate | 對單一候選做評分、成本估算、最小架構與 PoC proof question，作為進 Skill 4 前的決策報告。 |
| Skill 4 Validate | 只有在明確核准後才建立受控 AWS PoC，並留下 runtime、資源盤點與 cleanup 前證據。 |
| Skill 5 Report | 把 S1-S4 證據整理成主管可讀的結論、限制、成本邊界、cleanup 狀態與後續決策問題。 |

這讓專案從「AI 幫忙整理新技術」提升為「AI 協助建立可追責、可重跑、可交接的技術判斷流程」。

### 3. 用成功案例證明流程能落地

本期整理並強化 Lambda self-managed S3 code storage 與 S3 Files 兩個成功案例。

Lambda 案例證明：在受控 PoC 範圍內，Lambda 可以參照自主管理的 Amazon S3 code package，並完成建立、invoke、Console review 與 cleanup 證據整理。這個案例適合說明小型、邊界清楚的 AWS 新功能如何從官方來源一路走到 Skill 5 final report。

S3 Files 案例證明：Amazon S3 bucket 可以透過 S3 Files 以檔案系統方式掛載給 EC2 測試主機，並完成 S3 到 mount、mount 到 S3 的雙向讀寫驗證。它也展示了 Skill 4 不只是「部署成功」，還要保留 CloudFormation 資源盤點、權限與清除邊界，讓 Skill 5 能形成可審查報告。

需要保留的限制是：2026-08-13 重新跑的 S3 Files PoC 已完成部署與 runtime 驗證，但 cleanup 仍等待明確確認；因此它只能記為 cleanup 前的 interim 證據，不可寫成已結案。

### 4. 用停止案例證明流程能踩煞車

本期也把 WorkSpaces AI Agents 與 Amazon Quick Suite 整理成兩種不同的停止案例。
 
WorkSpaces AI Agents 來自 Skill 1 / Skill 2 的多候選掃描。AI 先整理多張 AWS 新功能候選卡，再由我選定 WorkSpaces AI Agents 進入 Skill 3。後續評估發現，雖然題目具備展示價值，但桌面代理、授權、合規、月費型成本與完整 AI session 證據不足，使它不適合直接進入 live Skill 4。

Amazon Quick Suite 則代表另一種停止理由：即使文章來自 AWS 官方，也可能主要是產品願景與效益宣稱，缺少可部署資源、IAM / data flow、成功條件與 cleanup 範圍。這讓 Skill 3 修正了可驗證性評分，避免因為 AI 想得出測試方法，就把缺乏實作細節的官方新聞推進 PoC。

這兩個案例讓成果發表更完整：系統不是只追求把 demo 做出來，而是能判斷何時不該花雲端資源。

### 5. 修正成本、核准與 cleanup 邊界

本期明確修正成本與部署語言。Skill 3 的成本估算一律是根據 AWS 公開牌價與明列用量假設產生的預部署估算，不是 AWS 帳單、正式採購報價，也不是公司實際費用。Skill 5 不再把短期 runtime facts 轉成實際帳務成本。

同時，流程也補強 human gate：即使候選分數達標，也只能代表「具備受控 PoC 資格」，不代表 AI 可以自動建立 AWS 資源。進入 Skill 4 前必須先讓人看到 Skill 3 報告、成本上限、PoC 要證明的問題、資源範圍、成功標準與 cleanup 設計，再由具名人員明確核准。

## 遇到的問題與解法

| 問題 | 解法 | 影響 |
|---|---|---|
| 官方文章容易被 AI 過度解讀成可部署方案 | Skill 1 區分可採信證據與待驗證推論；Skill 3 不讓 AI 推導提高可驗證性 | Quick Suite 被正確停在 Skill 3 |
| 技術新奇或文件完整容易讓 PoC 被高估 | Skill 3 改成五構面評分：技術價值、可驗證性、採用前提、可控制性、可逆性 | WorkSpaces 即使有展示價值，仍因成本與合規風險停止 |
| PoC 成功容易被寫成正式採用證據 | Skill 5 明確標示 intern / sandbox、公開價格估算、非正式帳務、非 production 驗證 | 對外說法更嚴謹 |
| 截圖直觀但不適合由程式自動判讀 | Skill 4 改以 structured resource inventory 作為主要證據，截圖只作人工輔助 | 證據更可審查與重跑 |
| 使用者要求完整流程時，AI 可能跳過 Skill 3 後的人工核准 | 新增規則：即使要求跑完整 S1-S5，也必須在 Skill 3 後暫停，取得明確部署核准 | 降低雲端資源與成本風險 |

## 學習與成長

本期最大的成長，是我開始把雲端實作從「會不會做出來」提升到「做這件事是否能支撐決策」。以前我比較容易把 PoC 當成技術展示；這兩週透過 Lambda、S3 Files、WorkSpaces 與 Quick Suite，我學到 PoC 的價值在於補足部署前無法回答的問題，例如帳號與 Region 是否可用、權限是否足夠、資源關係是否合理、runtime 行為是否符合預期，以及停止後能否清理與回查。

我也更理解 AI 協作的邊界。AI 可以協助搜尋、整理、寫程式、建立 artifact、檢查風險與產出報告，但它不能取代人類做成本、合規與是否部署的決策。這次成果發表能順利完成，也代表我逐步學會把 AI 的產出整理成可被人理解、可被質疑、也能回到證據查核的成果。

本期我完成了「預言者雷達」成果發表，並把雲端技術雷達從單純可執行的 PoC 流程，收斂成一套可由主管審查的技術決策方法。透過 Skill 1 到 Skill 5，系統能從 AWS 官方來源掃描新技術、比較候選、由人類選定單一候選、在部署前完成評分與成本估算，並在必要時進入受控 AWS PoC，最後產出證據報告。
