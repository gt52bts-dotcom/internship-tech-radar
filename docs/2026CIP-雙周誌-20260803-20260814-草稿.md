狀態：草稿。2026-08-10 09:15 先依 8/3、8/4、8/5 已完成日誌整理；8/6-8/14 仍需依後續正式日誌與實際成果補證據。

## 本雙周工作主軸

本期工作主軸是把雲端技術雷達從「可執行的 PoC 流程」收斂成「可讓主管審查的技術決策流程」。重點不再只是多做幾個 AWS 實驗，而是讓每個候選在進入 PoC 前先完成技術解釋、評分、成本估算、最小架構與人工核准；若真的進入 Skill 4，則必須保留部署結果、資源盤點、權限面、cleanup 前用量快照與清理回查，最後由 Skill 5 產出可交接的結案報告。

## 已完成工作

### 1. 重整 Skill 3 部署前決策流程

本期先修正原本「先選候選、後看成本」的資訊時序問題。新版流程改為先由 Skill 3 產出人類可讀決策報告，內容包含文章重點、技術前後差異、可能應用情境、PoC 最小架構、評分細項、成本估算、blocker 與是否建議進入 Skill 4。這讓人類在核准 PoC 前可以同時看到價值、成本與風險。

### 2. 將 PoC 判斷改成證據導向

本期把「這次 PoC 要證明什麼、成功後決策多知道什麼」寫入 Skill 3 與 Skill 4 的關卡。若一個候選在 Skill 3 就已經能判斷不值得投入，或 Skill 4 成功後也不會增加重要決策證據，流程就應停止，而不是因為技術新奇或分數看起來高就建立 AWS 資源。

### 3. 完成 Lambda 與 S3 Files 成功案例

Lambda self-managed S3 code storage 與 S3 Files 兩個案例被整理成可展示的成功範例。Lambda 案例驗證新的程式碼儲存模式可以建立、呼叫與清理；S3 Files 案例驗證 S3 bucket 以檔案系統方式掛載後，能完成 S3 到 mount、mount 到 S3 的雙向同步。兩個案例都能展示 Skill 3 決策報告、Skill 4 驗證證據與 Skill 5 報告價值。

### 4. 將 Skill 4 的確認方式從截圖改為資源盤點

原本 Skill 4 曾設計以 Console / Infrastructure Composer 截圖輔助人工確認，但後來確認程式不能可靠判讀圖片內容。因此本期把主要確認依據改為 structured resource inventory，記錄 CloudFormation 實際建立的資源、報價與部署資源是否一致、權限面、分段耗時與 cleanup 前用量快照。截圖只保留為輔助人工證據，不再作為主要驗證依據。

### 5. 修正 Skill 5 報告與成本邊界

本期移除短期 PoC 的實際帳務比對宣稱。Skill 5 報告改為清楚說明：Skill 3 的成本是公開價格表預估，不是正式採購報價，也不是 AWS Billing / Cost Explorer / CUR 帳務資料。Skill 5 的重點改為整理技術驗證、runtime evidence、資源盤點、cleanup 狀態、限制與 future work。

### 6. 制度化 AI PM 與跨電腦交接流程

本期把每個 Skill 收尾 checklist 寫入主專案與 handoff 版本，要求每階段結束前更新日誌或 inbox、說明驗證、檢查 Git 狀態、必要時提交與推送，並留下下一步。也恢復 AI 執行軌跡紀錄，將 GitHub、PROJECT_MEMORY、AI_PM_INBOX、正式日誌與每日軌跡定為跨 AI / 跨電腦接續來源。

### 7. 用 WorkSpaces AI Agents 驗證「不推薦 PoC」的價值

WorkSpaces AI Agents 原本因話題新、文件完整而容易被高估。後來本期重新修正 Skill 3 評分模型，把評分拆成技術價值、可驗證性、導入前置條件、可控制性與停止機制、可逆性與清理。WorkSpaces 最終因桌面畫面代理觀看可能需要合規覆核、完整 session 可能觸發月費型成本、第一階段 PoC 無法證明完整 AI 桌面任務，因此不推薦進入 live Skill 4。這個案例證明流程可以在 PoC 前踩煞車。

### 8. 準備 8/14 成果報告架構

本期已將 8/14 對協理的 30 分鐘成果報告收斂成電梯簡報架構：先完整介紹專案目的、詳細架構、使用方式、實作成果與整體成效，再展示 Lambda 與 S3 Files 兩個成功案例，接著說明 Skill 4 / Skill 5 的價值，最後用 WorkSpaces AI Agents 作為停止案例，說明系統如何避免不必要或不划算的 PoC。

## 本期成果與影響

- 技術評估從新聞摘要進化為決策證據鏈。
- PoC 前即可看到評分、成本、架構、blocker 與 proof question。
- Skill 4 不再只追求部署成功，而是保留可審查的資源、權限、runtime 與 cleanup 證據。
- Skill 5 報告更誠實地區分預估成本、runtime facts 與實際帳務。
- Lambda 與 S3 Files 提供正向成功案例，WorkSpaces 提供停止案例，能在成果報告中呈現流程能推薦也能否決。
- GitHub 與 AI PM 記錄機制降低跨 AI、跨電腦接續風險。

## 遇到的問題與解法

| 問題 | 解法 |
|---|---|
| 原流程容易在成本資訊不足時就讓人選候選 | 改成 Skill 3 先產出報價、架構與評分，再進人工核准 |
| 截圖看起來直觀，但程式不能可靠判讀圖片內容 | 改用 structured resource inventory 作為主要證據 |
| 短期 PoC 無法即時取得可靠帳務資料 | Skill 5 明確標示成本為預部署估算，不宣稱實際帳單 |
| 文件完整或技術新奇容易拉高分數 | 評分改成五構面，證據完整度只作 review note 或 blocker |
| AI 與不同電腦接續容易斷脈絡 | 建立 PROJECT_MEMORY、AI_PM_INBOX、daily log、GitHub 與 AI execution trace 的交接規則 |

## 學習與成長

本期最大的學習是把「把功能做出來」往前推進成「讓決策更可靠」。我不只要讓 AI 幫忙寫程式或報告，也要校正 AI 的判斷標準，避免它因為資料看起來完整或技術很新就推薦 PoC。透過 Lambda、S3 Files 與 WorkSpaces 三種不同案例，我學到 PoC 的價值不是部署本身，而是是否能補足 Skill 3 無法回答的決策證據，且完成後能不能留下可信且可清理的證據鏈。
