# S3 Files 新聞 PoC 收尾報告

## 結論

這次 PoC 的目標，是驗證 AWS 新聞裡的 S3 Files 是否真的能把 S3 儲存空間掛載成 EC2 可讀寫的檔案系統。最後結果是：最小情境驗證成功，S3 到 EC2、EC2 到 S3 的雙向資料路徑都已確認；測試完成後，相關 AWS 測試資源也已清理。

但這不是正式導入結論。這次只證明「單一 EC2 + 單一 S3 Files 掛載點」可行，還沒有驗證多機、壓力、長時間穩定性、故障復原或正式成本。

## 從新聞到評估

一開始的輸入是一篇指定 AWS News Blog，主題是 S3 Files 可以讓一般 S3 儲存空間被 EC2、container 或 Lambda 以檔案系統方式存取。因為這是使用者指定文章，不是當天 RSS 自動掃到的新聞，所以流程先把它標成「指定新聞輸入」，避免把來源寫錯。

技術雷達先做三層判斷：

1. 掃描：確認文章本身和主題有效，保留 1 個候選。
2. 比較：判斷它是否和目前 AWS 技術雷達主線相關，沒有被過濾掉。
3. 評估：依成熟度、AWS 適配性、企業案例、導入努力和風險做評分。

這篇新聞的核心訊號如下：

| 指標 | 分數 | 意義 |
|---|---:|---|
| 成熟度 | 5 / 5 | 服務已是正式可用狀態，不是 preview，因此可以進 PoC。 |
| AWS 適配性 | 5 / 5 | 它直接使用 S3、EC2、IAM、CloudFormation 等 AWS 服務，和目前專案主線高度一致。 |
| 風險 | 3 / 5 | 有檔案權限、網路掛載、同步延遲和成本管理問題，不能直接視為低風險。 |
| 導入努力 | 3 / 5 | 最小 PoC 可做，但需要建立網路、權限、掛載點與測試機，不是只開一個 S3 bucket。 |
| 企業案例 | 5 / 5 | 雷達找到多個和 S3 / Lambda / 金融或大型組織場景有重疊的案例，因此不是孤立技術。 |

評估階段的主評分是 4.5 / 5，驗證階段的交叉評分是 4.2 / 5，平均分是 4.35 / 5。這代表它值得進入 PoC，但仍需要人類審查，不應由 AI 自動開始建立付費資源。

## token、成本與 LLM 狀態

這次雷達流程原本預計使用外部 LLM 進行 S3 評估與 S4 驗證，但實際上沒有成功使用外部 LLM。

第一次失敗原因是 Lambda layer 缺少 Linux / Python 3.12 相容的原生模組；修正 layer 後再次執行，流程仍然成功跑完，但外部 API 回傳 invalid key。因此最後採用的是 rubric fallback，也就是用固定評分規則完成評估。

所以這次可確認的 token 狀態是：

| 項目 | 結果 |
|---|---:|
| 外部 LLM input token | 0 |
| 外部 LLM output token | 0 |
| 外部 LLM 實際費用 | USD 0.00 |
| 事前 quote gate 估算 | USD 0.0232 |

這一點很重要：報告不能寫成「Claude 已正式評分完成」。正確說法是：系統有嘗試走外部 LLM 評分，但因相容性與 API key 問題，最後使用規則式 fallback 完成本次評估。

Codex 在對話和實作過程中有協助判斷替代方案，但那不等於技術雷達的外部 LLM evaluator 成功產生 token。這兩件事要分開記錄。

## PoC gate 與人類同意

因為這篇新聞平均分 4.35，超過 3.75 的 PoC 門檻，且沒有治理阻擋旗標，所以系統把它標成「可以送人工 PoC 審查」。

這裡的規則是：AI 可以建議，但不能自己開始花錢建資源。真人仍要同意 PoC 範圍、成功標準、成本和 cleanup。

後來已確認 Cleo 有對正確的新聞 run 做出 approve，核准的是最小範圍 S3 Files PoC。核准內容的重點是：

- 只做最小驗證。
- 成功標準是 S3 和掛載資料夾可以雙向讀寫。
- 測完要確認成本和 cleanup。

## CDK、CloudFormation 和 CLI 的關係

這裡要分清楚兩條線。

第一條線是在前一天建立的 CDK PoC。當時目標是讓 Cleo 能從 CDK 產生 CloudFormation，再用 AWS Console 的 Infrastructure Composer 看懂資源關係。這一版曾遇到 CDK bootstrap / role assume 的限制，所以改成先產生 CloudFormation template，再用 AWS CLI 部署。這條線幫助確認「CDK 到 CloudFormation，再到 Console 視覺化」的學習路徑。

第二條線是這次新聞驅動 PoC。這次不是直接拿舊 CDK 專案再跑一次，而是根據新聞和官方文件整理出一份獨立 CloudFormation YAML，讓它代表這篇 S3 Files 新聞自己的最小架構。部署方式是用 AWS CLI 呼叫 CloudFormation，不是用 CDK deploy。

所以正確說法是：

- 7/22 的 CDK PoC：用 CDK 產 CloudFormation，再用 CLI 部署。
- 7/23 的新聞 fresh PoC：根據新聞和文件產生獨立 YAML，再用 CLI 部署到 CloudFormation。

這樣做的原因是避免混用舊 PoC 的成果，讓這次 PoC 可以回扣到「指定新聞進入 S1-S5 後，如何獨立產生可驗證實作」。

## 部署過程中的問題與修正

這次不是一路順利，有幾個重要問題：

1. 指定新聞第一次送進 Step Functions 時，輸入檔案有 UTF-8 BOM，AWS 拒絕讀取；後來改成無 BOM 的 JSON 才成功啟動。

2. 查歷史 execution 和重新啟動 gate 時，PowerShell 曾把 ARN 或 JSON 引號合併、破壞，導致 AWS CLI 拒絕請求；後來改用檔案輸入，避免命令列轉義問題。

3. 外部 LLM 評分沒有成功。第一層原因是 Python layer 相容性，第二層原因是 API key 無效。最後保留 fallback 評分，不把它寫成正式 LLM 成果。

4. PoC 部署後，EC2 可以掛載 S3 Files，但第一次用預設根目錄和寫入身分時遇到 POSIX 權限拒絕。這代表資源建起來不等於資料面成功，還必須處理檔案系統權限和掛載身分。

5. 修正方式是把 access point 的根目錄改成測試工作目錄，並指定一般測試使用者的寫入權限；再透過 Systems Manager 重新掛載和測試。

這些修正都影響判斷：如果只看 CloudFormation 顯示成功，會誤以為 PoC 完成；但實際上要到檔案能雙向讀寫，才算最小驗證成立。

## 驗證結果

最後做了兩個方向的資料面驗證。

第一個方向是 S3 到 EC2：

- 從 S3 放入一個有內容的測試檔。
- 到 EC2 掛載後的資料夾讀取。
- EC2 讀到相同內容，代表 S3 端資料可以透過 S3 Files 被機器看見。

第二個方向是 EC2 到 S3：

- 從 EC2 掛載資料夾寫入一個有內容的測試檔。
- 等待同步。
- 從 S3 讀回內容。
- S3 讀到 EC2 寫入的內容，代表掛載端寫入可以同步回 S3。

因此本次最小雙向資料路徑成立。

## cleanup 結果

測試完成後，先清空測試用 S3 儲存空間，再刪除 CloudFormation 建立的測試環境。這個順序很重要，因為 S3 有版本化物件時，如果沒有先清空，CloudFormation 可能刪不掉儲存空間。

收尾時也發現前一天留下的一套 S3 Files 測試環境仍有 EC2 在 running，會持續產生成本，因此一併清理。

最後回查結果：

- 沒有仍在運作的 S3 Files 測試環境。
- 測試用 EC2 都已刪除。
- 測試用 S3 儲存空間已刪除。
- S3 Files 檔案系統沒有殘留。
