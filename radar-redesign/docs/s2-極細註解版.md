# S2 極細註解版：把新聞變成可討論的提案卡

## 1. S2 的新定位

S2 不應只是「替 S1 補幾個 docs／pricing link」。真正的用途是：每一篇 S1 找到的真實新聞或開源候選，都變成一張能拿去討論的提案卡，並能橫向比較。

```text
S1 真實候選
  -> S2 重新核對來源與候選相關連結
  -> S2 Proposal Card（這個技術值得解什麼問題？）
  -> Comparison Matrix（各候選的改善假設、利弊與驗證門檻）
  -> 人類選最多 3 項進 S3
```

## 2. 為什麼 S0 的內容放進 S2

以前在入口先問「問題、預期改善、成功標準」，但使用者剛要探索新技術時，這些往往不知道答案。現在 S2 對每個已知候選個別問：

- 這項技術具體能改變哪個工作流？
- 要服務誰？目前 baseline 是什麼？
- 可能提升在哪個維度？來源有沒有量化證據？
- 要量什麼才算真的進步？
- 有何環境、成本、權限、治理、cleanup 代價？

因此 `proposal_card` 的 status 是 `candidate_hypothesis_requires_human_problem_selection`。它不是替你亂定公司需求，而是把你需要決定的空格列清楚。

## 3. 一張 Proposal Card 有什麼

| 區塊 | 內容 | 可不可以亂猜 |
| --- | --- | --- |
| candidate opportunity | 技術名稱、service signal、來源支持的能力摘錄 | 不可 |
| problem definition to confirm | 現在流程、目標使用者、baseline、成功條件 | 不可，未知就標 unknown |
| improvement hypothesis | 可能提升速度、流程自動化、開發效率、整合範圍或資源效率 | 可作假設，但標 hypothesis |
| improvement degree | 來源是否有 %、x、ms、seconds 等量化字樣 | 不可把質化敘述變成數字 |
| benefits | 為何值得看，每項附來源摘錄 | 不可 |
| tradeoffs and risks | 環境、治理、benchmark、整合等代價 | 可做 planning inference，但必須標示 |
| validation design | before/after 指標、最低成功證據、stop conditions | 必須可量測 |
| source boundary | primary source、連結證據數、覆蓋率 | 不可 |

## 4. 比較矩陣的指標

S2 不算一個假精準總分。它固定列出以下 10 個可以看出差異的欄位：

1. 技術範圍與偵測到的 AWS service。
2. 交付型態：SDK、compute instance、hybrid、desktop、regional extension、developer tooling 等。
3. 來源支持的能力摘錄。
4. 改善向量：效能／延遲、流程自動化、開發者效率、整合範圍、成本或資源效率。
5. 改善程度：來源有量化、只有質化、或完全沒有。
6. 環境訊號：是否提到 device、Swift、SAP ABAP、Kubernetes、on-prem、edge、region 等。
7. 成熟度：官方 GA 證據、未驗證、或非 AWS 官方來源不可判定。
8. 官方 docs、pricing、Region／availability 相關連結是否真的抓到。
9. 證據覆蓋率：8 個固定事實欄位中目前有多少被來源支持。
10. 決定性未知：商業問題、基準、權限、定價、區域、cleanup 是否仍未確認。

## 4.1 新加坡硬門檻

目標 Region 固定預設為 `ap-southeast-1`。S2 不接受「這個 AWS service 在新加坡有 endpoint」當成「這個新功能可在新加坡使用」的證明。只有候選相關的官方文章或官方文件明確出現 `ap-southeast-1`／`Asia Pacific (Singapore)`／Singapore，該候選的 `target_region_eligibility.status` 才是 `feature_level_region_verified`，可進 S3 shortlist。

否則它仍會保留在比較板裡供你查看，但狀態是 `not_eligible_until_feature_level_region_evidence`，S2 總狀態會是 `no_target_region_eligible_candidates`，而不是假裝可以做。

## 5. 利弊如何保持誠實

S2 分兩類：

- `source support`：來源原文真的提到的能力或數字。
- `planning inference`：依交付型態推得的驗證代價，例如 instance 要有代表性 baseline、hybrid 要看網路和身分邊界、desktop agent 要看治理與使用者控制。

兩者不能混寫。S2 會保留這個標籤，避免一張看似完整的卡其實把推論寫成事實。

## 6. 執行與讀結果

```powershell
python -m agentic_cloud_radar.cli s2 `
  --input .\out\s1-landscape.json `
  --output .\out\s2-landscape-proposals.json

$compare = Get-Content -Encoding utf8 .\out\s2-landscape-proposals.json -Raw | ConvertFrom-Json
$compare.status
$compare.comparison_matrix | Format-Table title, delivery_model, maturity, verified_dimension_count -Wrap
$compare.candidates[0].proposal_card
```

`ready_for_human_shortlist` 表示卡片已建立，不代表系統替你選好了。下一步是讀 matrix，挑最多三張卡，替每張補上真實 workflow、target user、baseline、成本與環境，再進 S3。
