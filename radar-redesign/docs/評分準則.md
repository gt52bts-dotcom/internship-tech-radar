# Skill 3 評分準則

本文件由 `agentic_cloud_radar/rubric.py` 產生，與實際評分讀取同一份定義，不會出現文件與行為不一致的情況。重新產生：

```powershell
python -m agentic_cloud_radar.cli rubric --output docs\評分準則.md
```

## SMI 對應

`SMI` 是 Service Measurement Index，這裡只拿來當雲服務評估面向的參考標籤，例如 Capability、Assurance、Agility、Accountability。它不另外計分，也不是另一個 gate；真正影響 Skill 3 結果的是構面分數、權重、否決門檻與 blocker。

## 彙總

| 構面 | 權重（加權計算） | 否決門檻 | SMI 對應 | 評的是什麼 |
| --- | ---: | :---: | --- | --- |
| 技術能力 | 0.3（分數 × 0.3） | — | SMI Capability | 這項能力相對於現有做法的改善幅度有多大？ |
| 證據可驗證性 | 0.2（分數 × 0.2） | ≤ 1 | SMI Assurance（證據可驗證性） | 新聞主張的核心能力，能否被一次受控實驗證實或推翻？ |
| 導入前置條件 | 0.2（分數 × 0.2） | — | SMI Agility | 導入所需的前置條件有多少、取得難度多高？ |
| 可控制性與停止機制 | 0.15（分數 × 0.15） | ≤ 2 | SMI Assurance（風險可停止性） | PoC 證據不支持原判斷、部署異常或前提不明時，AI/流程能否承認問題並暫停行動？ |
| 可逆性與終止 | 0.15（分數 × 0.15） | ≤ 1 | SMI Accountability / ISO/IEC 19086-1 可逆性與終止程序 | 停止之後，已發生的支出能否收回？ |

**加權分**：Skill 3 報告中的每一列加權分，都是該構面的 `分數 × 權重`。總分是所有構面加權分相加，滿分仍是 5 分。

**否決門檻**：任一構面分數觸及門檻，該候選一律不得進入 Skill 4，不論加權總分。加權總和是完全補償性彙總，單一構面的嚴重缺陷會被其他構面抵銷；設下限是為了讓那些缺陷無法被抵銷。

**通過門檻**：加權分 ≥ 3.75，且無否決、無 blocker。

## 技術能力（權重 0.3）

**評的是什麼**：這項能力相對於現有做法的改善幅度有多大？

### 判定所需的輸入與來源

| 欄位 | 由誰產生 | 用途 |
| --- | :---: | --- |
| `explanation.significance` | S1 | 以前／現在／差別三段對比 |
| `explanation.key_points` | S1 | 原文重點 |
| `proposal_card.improvement_hypothesis` | S2 | 改善假設向量 |
| `comparison_dimensions.delivery_model` | S2 | 交付模式 |

### 逐級判定條件

| 分數 | 條件 | 判定依據 | 為什麼是這一級 |
| :---: | --- | --- | --- |
| **5** | 原文明述可量化的改善（含數字與單位），且說明改善機制 | significance.difference 含數量詞，且 before／after 皆成立 | 有數字才談得上幅度；有機制才排除只是行銷語言 |
| **4** | 原文明述質性改善並說明機制，但未提供量化數據 | significance 三段完整，或改善向量存在且交付模式為受管服務 | 機制清楚即可判斷是否適用，缺數字只影響精確度不影響方向 |
| **3** | 原文宣稱改善，但未說明改善機制 | 存在改善向量，但 significance 缺 before 或機制描述 | 無機制則無法判斷改善是否適用於自身情境 |
| **2** | 屬既有能力的擴充（新區域、新規格、配額提高） | 改善向量或原文重點僅出現擴充類字樣 | 擴充改變的是可用範圍，不是做法本身 |
| **1** | 僅為介面或整合層的便利性改變 | 偵測到服務但無任何改善主張 | 便利性改變通常可由既有工具替代 |
| **0** | 原文未主張任何改善 | 無 significance、無改善向量、無偵測服務 | 無主張即無評估對象 |

## 證據可驗證性（權重 0.2）

**評的是什麼**：新聞主張的核心能力，能否被一次受控實驗證實或推翻？

### 判定所需的輸入與來源

| 欄位 | 由誰產生 | 用途 |
| --- | :---: | --- |
| `proposal_card.validation_design` | S2 | 驗證設計與成功證據 |
| `poc_recipe.recipe.success_criteria` | S3 | recipe 成功條件 |
| `explanation.significance` | S1 | 核心主張內容 |

### 逐級判定條件

| 分數 | 條件 | 判定依據 | 為什麼是這一級 |
| :---: | --- | --- | --- |
| **5** | 核心主張可由明確的通過／失敗條件驗證，且條件已寫入可部署 recipe | recipe 已登錄，且驗證設計含成功證據與前後量測 | 寫進 recipe 才代表驗證會真的執行，而非停留在設計 |
| **4** | 來源已提供足夠實作線索，且已有成功證據與前後量測，但尚未寫入 recipe | 驗證設計完整，且 S1/S2 至少能支撐最小架構與多個原文明述元件 | 設計必須被來源實作線索支撐，否則只是 AI 推導的測試想像 |
| **3** | 只能驗證部分主張，核心能力未納入成功條件 | recipe 已登錄但成功條件未涵蓋核心主張；或缺前後量測 | 能證明建得起來，不等於證明新聞說的效果 |
| **2** | 只能驗證周邊事實，核心主張無法檢驗 | 僅有成功證據或僅有前後量測其一 | 周邊事實不構成對主張的檢驗 |
| **1** | 來源缺少實作細節，無法定義來源支撐的可否證實驗 | 無 recipe 成功條件，且最小架構主要是 inferred/drafted 或只有一個原文明述元件 | 沒有資源清單、資料流、權限、成功條件或部署步驟時，PoC 設計只是推測，不能提高可驗證性 |
| **0** | 無任何可驗證內容 | 無主張亦無驗證設計 | 無可檢驗對象 |

## 導入前置條件（權重 0.2）

**評的是什麼**：導入所需的前置條件有多少、取得難度多高？

### 判定所需的輸入與來源

| 欄位 | 由誰產生 | 用途 |
| --- | :---: | --- |
| `region_status` | S2 | 目標區域證據狀態 |
| `poc_recipe.recipe.required_aws_services` | S3 | 所需服務數 |
| `poc_recipe.recipe.required_region_capabilities` | S3 | 所需區域能力 |
| `cost_estimate.quote.exclusions` | S3 | 授權與採購前提 |

### 逐級判定條件

| 分數 | 條件 | 判定依據 | 為什麼是這一級 |
| :---: | --- | --- | --- |
| **5** | 現有帳號可直接使用，無需申請、無需新環境 | 前置條件計數為 0 | 可立即開始，導入摩擦最低 |
| **4** | 需要建立標準資源，但無需申請或審核 | 前置條件計數為 1 | 可自行完成，不受他人排程影響 |
| **3** | 需要一項需申請或審核的前置條件 | 前置條件計數為 2 | 引入等待時間，但範圍可控 |
| **2** | 需要兩項以上前置條件，或需要新的授權模式 | 前置條件計數為 3，或報價載明授權待確認 | 多項並行等待，導入時程難以估計 |
| **1** | 需要組織層級變更或跨部門協調 | 前置條件計數為 4 以上 | 超出單一團隊可決定的範圍 |
| **0** | 現行環境無法滿足 | 區域明確不支援且無可接受替代 | 無法導入 |

### 前置條件的計數依據

分數 = 5 − 命中項數（最低 1）。命中的項目會列在報告的判定理由中。

- 目標區域未經功能層級確認
- recipe 需要兩項以上區域能力
- recipe 需要四項以上 AWS 服務
- 報價載明授權模式或採購前提待確認
- recipe 標記需要環境準備

## 可控制性與停止機制（權重 0.15）

**評的是什麼**：PoC 證據不支持原判斷、部署異常或前提不明時，AI/流程能否承認問題並暫停行動？

### 判定所需的輸入與來源

| 欄位 | 由誰產生 | 用途 |
| --- | :---: | --- |
| `proposal_card.validation_design.stop_conditions` | S2 | AI/流程何時必須停止或改成人工判斷 |
| `comparison_dimensions.unknowns` | S2 | 未知項目是否多到必須承認證據不足 |
| `poc_blockers / veto_violations` | S3 | 是否能把 blocker 視為暫停訊號，而不是硬做 PoC |

### 逐級判定條件

| 分數 | 條件 | 判定依據 | 為什麼是這一級 |
| :---: | --- | --- | --- |
| **5** | 停止條件已定義且可自動觸發，AI 能在證據不支持時停止下一步 | 停止條件存在，未知項少於四項，且有明確 abort / awaiting human gate 訊號 | 重點不是把流程跑完，而是能在判斷錯誤或證據不足時先停住 |
| **4** | 停止條件已定義，AI 能標出風險並等待人工判斷 | 停止條件存在，未知項少於四項 | 流程知道不能硬做，但暫停時機仍依賴人類確認 |
| **3** | 有停止條件但涵蓋不全，AI 可能太晚承認證據不足 | 停止條件存在，未知項四項以上 | 未知項太多時，AI 可能仍能停，但容易誤判何時該停 |
| **2** | 停止條件模糊，AI 只能事後標記風險，無法在行動前暫停 | 只有泛用風險提示，沒有明確 blocker、abort path 或人工 gate | 看得出有風險，但不足以阻止錯誤行動繼續發生 |
| **1** | 未定義停止條件，AI 無法知道何時該承認錯誤並暫停 | 無停止條件 | 沒有事先定義，模型容易把不確定當成可繼續推進 |
| **0** | 無任何中止途徑 | 無停止條件且無清除策略 | 無法停止 |

## 可逆性與終止（權重 0.15）

**評的是什麼**：停止之後，已發生的支出能否收回？

### 判定所需的輸入與來源

| 欄位 | 由誰產生 | 用途 |
| --- | :---: | --- |
| `cost_estimate.quote.scenarios[].line_items` | S3 | 費率表計價單位 |
| `poc_recipe.recipe.cleanup_strategy` | S3 | 清除策略 |
| `poc_recipe.recipe.cleanup_verification` | S3 | 清除後回查 |

### 逐級判定條件

| 分數 | 條件 | 判定依據 | 為什麼是這一級 |
| :---: | --- | --- | --- |
| **5** | 資源清除即停止計費，且 recipe 已宣告清除策略與清除後回查 | 費率表無非按比例計費項目，且清除策略與回查皆已宣告 | 宣告清除與驗證清除是兩回事，兩者齊備才算可逆 |
| **3** | 含持續計費資源，但未宣告清除策略或回查 | 費率表含小時計費項目，recipe 未宣告清除或回查 | 可停但無人確認是否真的停了 |
| **1** | 費率表存在不隨清除退回的費用 | 計價單位或公式含按月計收、預付或最低承諾 | 清除對這部分支出無效，成本在啟動瞬間即已固定 |
| **0** | 無明確清除途徑 | recipe 未宣告清除策略且無資源範圍 | 無法終止 |

## 兩條共通規則

**不得為特定候選寫死分數。** 每一級的判定條件都必須是任何候選都適用的訊號。若某個候選得到不合理的分數，要修的是訊號定義，不是為它加一個分支——否則評分準則就退化成查表，個案結果也不能作為方法有效的證據。

**證據不足與表現不佳要分開。** 缺乏證據時給中間值並在理由中標明；確實表現差才落到否決門檻。把兩者混為一談，會讓「文件寫得少」看起來像「技術不好」。
