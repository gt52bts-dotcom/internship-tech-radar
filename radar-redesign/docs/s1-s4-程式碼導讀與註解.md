# S1-S4 程式碼導讀與註解：規則引擎、人工 gate 與真實 PoC 的分工

這份文件對照目前的 `agentic_cloud_radar/` 程式碼。它回答兩件事：資料怎麼從一篇新聞走到 S4，以及哪些步驟是固定、可重跑的程式，哪些需要人或 Codex 協助。它不是 S5 報告，也不把本機 S4 validator 說成會自行建立 AWS 資源。

## 1. 一張總地圖

```text
CLI JSON input
  -> S1: fetched public source + scan artifact
  -> S2: refetched official evidence + proposal cards
  -> S3: human shortlist + fixed rubric + evaluation artifact
  -> S4: approval checks + validation artifact
  -> optional external PoC runner: deployment context -> CDK synth -> CloudFormation -> evidence
```

`cli.py` 是唯一的命令列路由層。每個子命令只讀取上一階段 JSON、呼叫一個 `build_*` 函式，再寫出 JSON；它不把前一輪的文章摘要、AI 記憶或任意資料夾檔案偷偷混進來。輸入採 `utf-8-sig`，所以 PowerShell 5.1 產生的 UTF-8 BOM JSON 也能讀。

## 2. Artifact 契約為什麼重要

| 階段 | 主要函式 | 允許輸入 | 產物保證 |
|---|---|---|---|
| S1 | `build_scan()` / `build_direct_url_scan()` | discovery request 或使用者直接貼的 HTTPS URL | 每個候選含來源、抓取結果、服務偵測、資料缺口 |
| S2 | `build_compare()` | S1 狀態為 `scanned` 或 `scanned_with_gaps` | 每候選一張 proposal card；所有「已證實」內容可回查 URL |
| S3 | `build_evaluate()` | S2 狀態 `ready_for_human_shortlist` 加人工短名單 | 固定權重分數、信心、stop conditions、唯一 `recommend_poc` 決策與完整 PoC 報價 |
| S4 | `build_validate()` | S3 狀態 `evaluated`，可附 approval | 受控 PoC 的 approval gate；`automatic_poc_start` 永遠為 `false` |

因此，某個 artifact 少了的資訊，下一階段應顯示 `unknown` 或 data gap，不該由程式或 LLM 補寫成事實。

## 3. S1：取得可追溯的原始證據

檔案：[s1.py](../agentic_cloud_radar/s1.py)。

### 3.1 兩個入口

- `build_direct_url_scan(url)`：給「我就是想看這篇」的情境。先檢查 HTTPS、host allowlist、redirect 後的 host 和 HTML content type，再擷取本文。
- `build_scan(request)`：給雷達探索。`_fetch_aws_blog_catalog()` 在執行當下讀 AWS Blogs 目錄，`_select_aws_blog_feeds()` 根據 scope 選分類 RSS，並保留 AWS What's New。這是保留 AWS Blog 分類深度的關鍵，不是固定幾條手寫 feed。

### 3.2 為何需要 `_fetch_trusted_html_url()`

它把對外 HTTP 收斂為一個出口：送出 user agent、限制逾時、確認最終 redirect 仍在 allowlist、拒絕非 HTML。`_HtmlTextExtractor` 去掉導覽和頁面框架，再以 `MAX_ARTICLE_TEXT_CHARS` 限制 artifact 大小。它只整理取得的文字，不理解或改寫技術結論。

### 3.3 候選如何產生

`_candidate_from_fetched_source()` 將真實頁面轉成候選：

- `candidate_id` 是 run ID、標題和 URL 的雜湊，避免名稱相同時混淆。
- `service_detection.py` 用明確 alias 規則找服務名稱；這是文字提及，不是架構依賴圖。
- `_maturity_evidence()` 只接受明確 GA wording。找不到不代表 preview，只代表「此來源未證實 GA」。
- `initial_claims` 最多保留三段原文，讓 S2 不必憑空產生 capability。

## 4. S2：把新聞轉成可審核的提案卡

檔案：[s2.py](../agentic_cloud_radar/s2.py)。`build_compare()` 先用 `_validate_s1()` 拒絕無法使用的 S1，再逐候選呼叫 `_compare_candidate()`。

### 4.1 證據再抓一次，而不是相信 S1 摘要

`_collect_source_evidence()` 會重新抓 S1 原文、挑出候選相關的官方 docs/pricing/Region 連結，並以 AWS 公開搜尋索引補找未被新聞連結的官方頁面。搜尋結果只用來發現 URL；真正寫進 evidence 的是 `_fetch_official_page()` 再抓到的頁面。

這裡的防呆很重要：來源中出現 Singapore 但其實在談別的功能，不能當作此候選可用。`_target_region_matches()` 要求同一句同時有 target Region 與候選特徵。另一個正式例外是「all commercial AWS Regions」：對已知商業區的 `ap-southeast-1`，只要同一句也提到此候選偵測到的服務，就可當成官方功能級可用證據；一般的「AWS Regions」行銷句不會通過。

### 4.2 Proposal Card 的三種語氣

- `source_backed_capabilities`：原文片段支持的事實。
- `improvement_hypothesis`、benefits、trade-offs：規劃假說，必須保留限制說明。
- `unknowns_and_next_validation_question`：缺定價、區域、公司情境或權限時，不猜答案，改成下一步問題。

S2 可輸出多張卡和 comparison matrix，但 `automatic_shortlist` 是 false。選哪個技術仍是人做。

## 5. S3：固定 rubric，不能因喜歡候選而換權重

檔案：[s3.py](../agentic_cloud_radar/s3.py)。`_human_shortlist_gate()` 只接受一個 candidate ID；不再要求公司問題、使用環境或資料限制表單。

`_evaluate_candidate()` 的分數由下列固定權重組成：

```python
technical_value = 0.35
adoption_prerequisites = 0.25
verifiability = 0.25
risk_and_stop_conditions = 0.15
```

四個 `_..._score()` 函式各回傳 0 到 5，`weighted_score` 只做加權加總。成本刻意不放進技術分數，只以 `unknown` 或後續上限檢查記錄。`_confidence()` 根據已驗證維度、unknown 數量和短名單是否完整計算 high/medium/low。

`region_unknown` 只在 adoption 前提扣分並留下 `poc_review_notes`，不再阻擋 PoC 審查。Bedrock 或 `blocks_s3` 才是 hard blocker；`eligible_for_poc_review` 直接依公開證據分數、信心與 hard blocker 判斷。

## 6. S4：本機 validator 與真實 PoC runner 是兩個東西

檔案：[s4.py](../agentic_cloud_radar/s4.py)。目前 `build_validate()` 是**不會建立資源**的規則驗證器。它把 S3 結果包成 `s4.validation.v2`，並透過 `_poc_checks()` 檢查：

1. S3 是否達到 `eligible_for_poc_review`。
2. 是否指定真人 `approved_by`。
3. 內建或覆寫的成本上限是否在 policy 內。
4. `automatic_poc_start` 是否保持 false。

少任一項都不會部署，只會產生 `validated_low_risk` 與 `downgrade_reasons`。Region、profile、success criteria 與 cleanup scope 使用系統預設，不再要求使用者逐欄設定。

前一次 S3 Files 的完整 S4 使用的是**獨立的 S3 Files PoC 模組**：先從該次 S1/S2/S3 artifact SHA-256 產生 deployment context，再由 [app.py](../../poc/s3-files-cdk-poc/app.py) 呼叫 [stack.py](../../poc/s3-files-cdk-poc/s3_files_cdk_poc/stack.py) synth 出 CloudFormation；最後由 AWS CloudFormation 建立、SSM 驗證、CloudFormation 刪除。Lambda self-managed S3 code storage 也有自己的 [CDK recipe](../../poc/lambda-self-managed-storage-cdk-poc/)；每個新候選都必須有自己的 recipe，不能互相套用。

## 7. LLM、程式與人各做什麼

目前 runtime 沒有呼叫 LLM API 來選結論：HTTP 擷取、服務提及、GA 比對、Region 規則、S3 加權、S4 gate 都是 deterministic code。Codex 的價值在設計規則、將 artifact 串成可執行流程、判讀真實錯誤與協助人類讀結果；人類負責選擇研究方向、批准或拒絕資源操作、驗收結果。

因此要把系統產品化，應把常態流程放在可測的 S1-S4 code，將 LLM 留在研究輔助、例外排障和解釋，而非讓它繞過 evidence、成本或人工核准。

## 8. 讀程式與重跑順序

```powershell
Set-Location C:\Users\youhs\Documents\實習專案\radar-redesign
python -m unittest discover -s tests -v

python -m agentic_cloud_radar.cli s1-url --url "<AWS 公開 URL>" --output .\out\run\s1.json
python -m agentic_cloud_radar.cli s2 --input .\out\run\s1.json --output .\out\run\s2.json
# 人確認 shortlist.json 後才執行：
python -m agentic_cloud_radar.cli s3 --input .\out\run\s2.json --shortlist .\out\run\shortlist.json --output .\out\run\s3.json
python -m agentic_cloud_radar.cli s4 --input .\out\run\s3.json --output .\out\run\s4.json
```

檢閱時先看每份 JSON 的 `status`、`run_id`、`policy_ref`、`source_url`、`evidence_limits`；再看 Skill 3 的 `stop_conditions` 與 Skill 4 的 `poc_checks`。這比只看最後分數更能發現資料斷點。
