# S1 極細註解版：先蒐集真實候選，不先填空泛需求

## 1. S1 現在做什麼

S1 是資料入口，不是需求審核。它有兩條獨立通道：

| 通道 | 指令 | 何時用 | 是否經過 S0 |
| --- | --- | --- | --- |
| 直接匯入 | `s1-url --url` | 已有一篇 AWS／開源文章或專案頁要看 | 否 |
| 技術探索 | `s1 --input` | 想從 AWS Blogs、RSS、GitHub 看近期或 GA 技術 | 否 |

這個拆法很重要：貼 URL 本身已經是使用者明確選擇；想探索技術時，尚未知道公司痛點也很正常。S1 的工作是先把真實候選與來源帶回來，S2 再替每個候選建立問題與改善假設。

## 2. URL 匯入：`s1-url`

```powershell
python -m agentic_cloud_radar.cli s1-url `
  --url "https://aws.amazon.com/blogs/aws/launching-s3-files-making-s3-buckets-accessible-as-file-systems/" `
  --output .\out\s1-s3-files.json
```

執行順序：

1. 檢查 URL 不是空白。
2. 檢查 `https` 與 host allowlist：AWS、GitHub、GitLab、Codeberg。
3. 真的送 HTTP request。
4. redirect 後再次檢查 host，避免轉到未知站台。
5. 檢查回應是 HTML。
6. 解析 title、meta description、可讀文字。
7. 產出一筆 candidate；`entry_point.type=direct_url_import`、`demand_card_ref=null`。

`demand_card_ref=null` 不是錯誤。它表示系統沒有捏造商業問題，S2 會因此把 business fit 標為 unknown。

## 3. 技術探索：`s1`

```json
{
  "discovery_scope": "landscape",
  "max_source_age_days": 3650,
  "max_candidates": 12,
  "maturity_requirement": "ga_evidence_required",
  "constraints": { "excluded_services": ["Bedrock"] }
}
```

```powershell
python -m agentic_cloud_radar.cli s1 `
  --input .\out\landscape-request.json `
  --output .\out\s1-landscape.json
```

### 3.1 AWS 來源不是手寫清單

S1 每次都先讀 `https://aws.amazon.com/blogs/`，解析當下的分類目錄，再讀各分類 RSS。這能覆蓋 Architecture、Artificial Intelligence、Cloud Operations、Big Data、Compute、Storage、Security、Open Source 等，而不是只盯 CI/CD。

- `focused`：把可選 hint 轉成分類選擇理由。
- `landscape`：跨分類取得候選，適合做全方位技術地圖。
- `max_source_age_days`：候選文章可接受的最長年齡。
- `max_candidates`：最終保留的數量上限。
- `constraints.preferred_region`：預設 `ap-southeast-1`。S1 保留候選，但 S2 會以「功能級新加坡可用性」決定能否進 shortlist。

### 3.2 GA 模式

當 `maturity_requirement=ga_evidence_required`：

1. RSS 標題／摘要先找 `general availability` 類字樣。
2. 抓回真正官方文章原文。
3. 只保留原文也有明確 GA 語句的 AWS 候選。
4. Preview、未來才 GA、roundup 回顧文章不會被當成單一 GA 技術。

這是來源證據篩選，不是完整 AWS release archive，也不會把「沒有看到 GA」誤寫成「一定不是 GA」。

### 3.3 GitHub 搜尋

非 GA-only 時，S1 會用 GitHub Public Repository Search 找公開候選，保存 query、API URL、stars、forks、license、topics、更新時間與 archived 狀態。GitHub metadata 不能證明 AWS GA，所以 GA-only 時會跳過這一支。

## 4. S1 artifact 的關鍵欄位

```json
{
  "stage": "S1",
  "entry_point": { "type": "technology_discovery", "s0_required": false },
  "candidates": [
    {
      "title": "來源頁面的真正標題",
      "source_url": "最終 redirect URL",
      "official_source": true,
      "external_fetch_performed": true,
      "related_aws_services": ["偵測到的 service"],
      "initial_claims": ["從來源萃取的句子"],
      "maturity_evidence": { "status": "..." },
      "data_gaps": []
    }
  ]
}
```

S1 不產生推薦、分數、成本結論或 PoC 計畫。它只交付證據候選與缺口；S2 才把每筆候選做成提案卡。

## 5. 最常用的檢查指令

```powershell
$scan = Get-Content -Encoding utf8 .\out\s1-landscape.json -Raw | ConvertFrom-Json
$scan.status
$scan.candidates.Count
$scan.candidates | Select-Object title, source_url, official_source, open_source
```

可能狀態：

- `scanned`：候選都有且沒有資料缺口。
- `scanned_with_gaps`：有候選，但某些 RSS／文章／上下文證據缺少；這是誠實結果，不是掃描失敗。
- `needs_revision`：掃描參數或 URL 無效。
- `no_candidates`：當次真實來源沒有留下符合條件的候選。

## 6. 程式閱讀地圖：資料到底怎麼流

想從程式理解 S1，建議按照下面順序讀，而不是從中間的 RSS parser 開始：

1. `cli.py` 的 `_run_s1` 與 `_run_s1_url`：讀 JSON、呼叫 S1、把 artifact 寫成 UTF-8 JSON。這裡不替資料補值。
2. `s1.py` 的 `build_scan()`：Discovery 主流程。它先檢查掃描參數，再讀 AWS Blogs 分類與 RSS，最後才視模式加上 GitHub 搜尋。
3. `s1.py` 的 `build_direct_url_scan()`：URL Import 主流程。它只信任使用者指定且通過 host／redirect／HTML 檢查的公開頁。
4. `_candidate_from_fetched_source()`：把真實抓回的 title、description、本文、服務訊號與缺口整理成一筆候選；不是人工填一個 service 名稱。
5. `_maturity_evidence()`：GA-only 的守門人。它檢查原文語境，排除 Preview、未來才 GA、roundup，避免只因看到 "general availability" 字串就誤放行。

```text
Discovery request / public URL
  -> 來源與參數檢查
  -> 實際 HTTP fetch
  -> HTML / RSS 解析
  -> 文章層候選與 GA 證據
  -> s1.scan.v2 artifact
  -> S2
```

## 7. S1 會做與不會做的判斷

S1 可以判斷「這是本次抓到的可信公開來源」、「原文有沒有明示 GA」、「文章可能涉及哪些 AWS service」。它不能判斷公司是否需要此技術、功能是否真的適合某個工作流、成本是否合理，或是否已在新加坡可用。

最後一項尤其重要：`target_region` 在 S1 request 只是後續 S2 的取證目標，不能因為服務通常有新加坡 endpoint，就在 S1 把候選寫成可用。功能級 Region 證據會留給 S2 查找與審核。

## 8. 哪些情況會讓 S1 結果不完整

- RSS 每個 feed 只取最新 20 項，所以 `max_source_age_days=365` 是時間上限，不是已讀完一年 archive 的保證。
- AWS Blog 分類目錄、單一 feed 或文章可能暫時無法抓取；artifact 會留下 warning 或 data gap，不會用快取或虛構內容補洞。
- GitHub 的 stars、license 與更新時間只能描述開源專案，不可被當成 AWS GA 或公司可部署的證據。
- 網頁正文解析無法完全理解圖表、互動元件或登入後內容；S1 保留其取到的可讀文字，不會把未抓到的部分猜回來。

## 9. 我如何自己重跑一次

先準備只含掃描條件的 JSON；不要貼一段改寫過的新聞內容。執行 S1 後，先檢查 `status`、`source_catalog`、每筆 candidate 的 `source_url`、`external_fetch_performed` 與 `maturity_evidence`。只有這些都能回查，才把 artifact 交給 S2。
